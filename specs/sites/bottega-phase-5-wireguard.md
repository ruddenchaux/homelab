# Bottega Phase 5: WireGuard Hub

## Summary

- **Site**: Bottega
- **Phase**: 5, inbound WireGuard and the road-warrior peer
- **Goal**: open UDP `61536` from `WAN`, terminate WireGuard on the router
  itself, and give the road-warrior peer access to the Bottega lab VLANs —
  making Bottega the hub `specs/network/topology.md` describes.
- **Primary specs**: `specs/sites/bottega.md`, `specs/network/wireguard.md`
- **Implementation**:
  `ansible/playbooks/bottega-phase-5-wireguard.yml`

This is the second and last WAN exception on Bottega. After it, the router
answers exactly two things from the internet: TCP `443` (phase 4) and UDP
`61536` (this phase). Nothing else is ever opened directly.

## Scope and Non-Goals

Phase 5 creates exactly:

1. One WireGuard interface `wg-hub`, `listen-port=61536`, `mtu=1412`, whose
   private key RouterOS generates and never exports.
2. The tunnel address `10.99.0.1/32` on that interface, and `wg-hub` as a
   member of the `LAN` interface list — never `WAN`.
3. One input-chain accept for UDP `61536` arriving on `WAN`, inserted before
   the final `drop in-interface-list=WAN`.
4. One WireGuard peer for the road-warrior at `10.99.0.11/32`, with no
   `endpoint-address` and no `persistent-keepalive`.
5. One forward accept from `wg-hub`, `src-address=10.99.0.11`, to the
   `bottega-lab-vlans` address list, placed before the first enabled forward
   drop.
6. One `change-mss` mangle rule clamping TCP MSS to PMTU on traffic leaving
   through `wg-hub`.
7. One static route to `10.99.0.11/32` via `wg-hub` — RouterOS does not derive
   this from the peer's `allowed-address` on this build (confirmed, see
   "Facts Confirmed on the Router" below), so it is an owned object, not an
   assumption.
8. `10.99.0.0/24` added to the `/ip service` address list for `www`, `ssh`,
   and `winbox`.
9. A road-warrior client profile and QR code, rendered locally, never
   committed.

This phase does not:

- add the Casa spoke peer, or any forward rule toward Casa;
- renumber Casa's LAN;
- open TCP `80`, add hairpin NAT, or change the phase 4 dst-nat path;
- enable RouterOS `/ip cloud`;
- remove the Hetzner VPS, its tunnel, or its road-warrior peer;
- change VLANs, subnets, DNS, or Wi-Fi.

### Why Casa is a separate phase

`AGENTS.md` #3 requires both ends of a peer in one change. The road-warrior's
"other end" is a client profile this phase generates, so that rule is satisfied.
Casa's other end is a second router that is not in inventory, needs its own age
recipient and SOPS file (`AGENTS.md` #1), and needs its LAN renumbered from
`192.168.88.0/24` to `192.168.90.0/24` to stop overlapping Bottega's VLAN 1
(`AGENTS.md` #2) — a remote-router change that can strand the site. Bundling it
here would mean applying a renumber and a new listener in the same window.

- [ ] The input chain matches either the phase 2 baseline or the converged
      phase 5 chain — nothing in between.
- [ ] A road-warrior keypair exists in `ansible/secrets/bottega.sops.yml`.
- [ ] The existing VPS road-warrior profile still works, and has been tested

- [ ] A current `/export hide-sensitive` is stored off-router.
- [ ] RouterOS interactive safe mode or a tested timed rollback is ready, and
      the operator is cabled to `ether2`–`ether4` with MAC-WinBox available.
- [ ] `qrencode` is installed locally.

The playbook will not mutate RouterOS unless these are all true:

```text
bottega_phase5_router_recovery_confirmed=true
bottega_phase5_external_baseline_confirmed=true
bottega_phase5_vps_fallback_available_confirmed=true
```

## Credentials

The hub's private key is generated by RouterOS and stays there. Only the
road-warrior keypair is stored, and only in Bottega's SOPS file:

```sh
wg genkey > /tmp/rw.key && wg pubkey < /tmp/rw.key
cd ansible
sops set secrets/bottega.sops.yml \
  '["bottega_wg_roadwarrior_private_key"]' '"ACTUAL_PRIVATE_KEY"'
sops set secrets/bottega.sops.yml \
  '["bottega_wg_roadwarrior_public_key"]' '"ACTUAL_PUBLIC_KEY"'
shred -u /tmp/rw.key
```

The committed values are placeholders; preflight rejects anything that is not a
44-character base64 key. `.sops.yaml`'s first-match rule encrypts this file for
Bottega's age recipient only — do not move these values to
`ansible/secrets.sops.yml`.

## Required RouterOS State

Owned interface:

```text
name=wg-hub listen-port=61536 mtu=1412 disabled=no
comment=bottega-phase5-wg-hub
```

Owned address:

```text
address=10.99.0.1/32 interface=wg-hub
comment=bottega-phase5-wg-address
```

Owned peer:

```text
interface=wg-hub
public-key=<road-warrior public key>
allowed-address=10.99.0.11/32
endpoint-address=          # empty: the hub answers, it never dials
comment=bottega-phase5-peer-roadwarrior
```

Owned forward accept:

```text
chain=forward action=accept
in-interface=wg-hub
src-address=10.99.0.11
dst-address-list=bottega-lab-vlans
comment=bottega-phase5-fwd-roadwarrior
```

Owned route:

```text
dst-address=10.99.0.11/32 gateway=wg-hub
comment=bottega-phase5-route-roadwarrior
```

Owned MSS clamp:

```text
chain=forward action=change-mss new-mss=clamp-to-pmtu passthrough=yes
protocol=tcp tcp-flags=syn out-interface=wg-hub
comment=bottega-phase5-wg-mss-clamp
```

Owned input exception, declared in `ansible/inventory/group_vars/mikrotik.yml`
and installed by the base-lockdown role:

```text
chain=input action=accept protocol=udp dst-port=61536
in-interface-list=WAN
comment=Bottega phase 5 input 03a accept-wireguard
```

The input chain becomes five rules, in this order, with the WAN drop still
last:

```text
1  accept connection-state=established,related
2  drop   connection-state=invalid
3  accept in-interface-list=!WAN
3a accept protocol=udp dst-port=61536 in-interface-list=WAN
4  drop   in-interface-list=WAN
```

### Per-peer scoping is by src-address, not interface

Casa and the road-warrior both terminate on `wg-hub` — one listener, one port.
`in-interface=wg-hub` therefore cannot tell them apart, and any rule meant for
one peer must also match on `src-address`. The Casa phase must follow the same
pattern; using the interface alone would silently grant Casa's entitlements to
every road-warrior and vice versa.

### The input chain is owned by the base-lockdown role

Phase 5 does not add its input rule directly. `mikrotik-bottega-base-lockdown`
models the whole chain and rebuilds it with
`/ip firewall filter remove [find where chain=input]` whenever its readback
drifts, so a rule added behind its back would be deleted on the next run of
`bottega-base-lockdown.yml` — dropping a live tunnel, which is exactly the
remote-lockout failure `AGENTS.md` #4 exists to prevent. The exception is
declared once in `ansible/inventory/group_vars/mikrotik.yml` and every playbook
that touches this router shares that declaration. See
`ansible/roles/mikrotik-bottega-base-lockdown/README.md`.

One consequence worth knowing: because the declaration is checked in, running
`bottega-base-lockdown.yml` on its own opens UDP `61536` even if `wg-hub` does
not exist yet. That is harmless — a port with no listener behind it is
indistinguishable from a closed one to an external scanner — but it means the
declaration and the interface should land together.

### Facts Confirmed on the Router

- `/ip route print where gateway=wg-hub` does **not** gain a dynamic route to
  the peer's `allowed-address` on this hAP be3 build. A `/32` interface
  address leaves no connected route to fall back on, so without the owned
  static route above, the tunnel handshakes but return traffic to the
  road-warrior black-holes. Discovered empirically during the first live
  application of this phase; the static route is now part of the owned state
  this role converges and validates, not a manual follow-up step.
- The factory forward `drop` that is enabled by default is scoped
  `connection-state=invalid`, which is not `WAN`-scoped, so the road-warrior
  forward accept placement logic finds it (not the phase-4-relevant
  `in-interface-list=WAN` drop) as the first drop to move ahead of. This is
  harmless — the accept still lands before every enabled drop in the chain —
  but future forward-chain additions should be aware placement is chain-wide,
  not WAN-scoped.

### Management over the tunnel

`/ip service` for `www`, `ssh`, and `winbox` grows from `192.168.88.0/24` to
`192.168.88.0/24,10.99.0.0/24`. This is a LAN/VPN grant per
`specs/network/firewall.md`, not a WAN exposure: the overlay is only reachable
after a completed WireGuard handshake. Tightening the LAN half of that list to
VLAN 10 remains deferred in `specs/sites/bottega.md`.

## Conflict Handling and Change Order

Preflight refuses to mutate anything if:

- the input chain matches neither the phase 2 baseline nor the converged phase
  5 chain;
- `bottega_mikrotik_input_exceptions` does not declare exactly the phase 5
  rule, or `bottega_mikrotik_management_subnets` omits the overlay;
- a WireGuard interface other than `wg-hub` already listens on `61536`, or a
  non-owned peer, forward rule, or mangle rule already references `wg-hub` or
  `10.99.0.11`;
- an owned object exists more than once, or has drifted in its enabled state,
  interface, address, key, port, MTU, or scope;
- the phase 4 dst-nat/forward rules are missing or drifted;
- the lab-VLAN address list contains an entry that is not one of the three
  VLANs.

Convergence creates the interface before anything that references it by name,
then adds policy before the listener becomes reachable:

1. Create `wg-hub`, then its address, then its `LAN` membership.
2. Add the road-warrior peer.
3. Add the static route to the road-warrior's overlay address.
4. Add the `bottega-lab-vlans` address-list entries.
5. Add the road-warrior forward accept, then move it before the first enabled
   forward drop.
6. Add the MSS clamp.
7. Install the input exception by rebuilding the chain through the
   base-lockdown role.
8. Extend `/ip service` to the overlay.
9. Strictly read back everything, plus the phase 4 rules and LAN/WAN
   separation.

Step 1 has to come first: `community.routeros.command` does not surface
RouterOS's rejection of a command referencing a nonexistent interface as an
Ansible failure, so any rule added before `wg-hub` exists fails silently
rather than loudly. The input exception — the only step that actually opens
anything to `WAN` — stays last.

The listener is the last thing to become reachable, so there is no window where
traffic can arrive before the rules that constrain it exist.

## Safe Application

Follow `.claude/skills/mikrotik-safe-change.md`. Ansible does not turn on
interactive safe mode, so the operator provides the backstop. From `ansible/`:

```sh
ansible-playbook playbooks/bottega-phase-5-wireguard.yml \
  -e bottega_phase5_router_recovery_confirmed=true \
  -e bottega_phase5_external_baseline_confirmed=true \
  -e bottega_phase5_vps_fallback_available_confirmed=true
```

Then re-run the same command — the recap must report `changed=0` — and re-run
the two playbooks this phase's refactor touches:

```sh
ansible-playbook playbooks/bottega-base-lockdown.yml
ansible-playbook playbooks/bottega-phase-4-public-https.yml \
  -e bottega_phase4_external_closed_baseline_confirmed=true \
  -e bottega_phase4_router_recovery_confirmed=true \
  -e bottega_phase4_vps_rollback_available_confirmed=true
```

Both must report `changed=0` and pass their own validation. This is the real
regression test: before the declared-exceptions refactor, the first would have
deleted the WireGuard rule and the second would have failed its preflight.

## Rollback

Under safe mode, removing policy only after the thing it protects:

1. Remove the peer:

   ```routeros
   /interface wireguard peers remove \
     [find where comment="bottega-phase5-peer-roadwarrior"]
   ```

2. Set `bottega_mikrotik_input_exceptions: []` in
   `ansible/inventory/group_vars/mikrotik.yml` and re-run
   `bottega-base-lockdown.yml`. This rebuilds the four-rule chain and closes
   UDP `61536`.
3. Remove the MSS clamp, the forward accept, the `bottega-lab-vlans` entries,
   and the static route to `10.99.0.11/32`, then `/ip address` and
   `/interface wireguard` for `wg-hub`.
4. Revert `bottega_mikrotik_management_subnets` to `192.168.88.0/24` and re-run
   the base lockdown.
5. Repeat the phase 3 external closed-port baseline and the phase 4 checks.

Never remove the input exception before the peer, and never remove the
interface before the rules that reference it. The phone's VPS profile stays
valid throughout, so remote access never depends on the path being changed.

## Acceptance Criteria

Router, from a host on `192.168.88.0/24`:

- [ ] `/interface wireguard print` shows exactly one `wg-hub` with
      `listen-port=61536` and `mtu=1412`.
- [ ] `/ip address print` shows `10.99.0.1/32` on `wg-hub`.
- [ ] `/interface list member print` shows `wg-hub` in `LAN`, not in `WAN`,
      and no interface in both lists.
- [ ] `/ip firewall filter print chain=input` returns the five rules above, in
      that order, with `drop in-interface-list=WAN` last.
- [ ] Exactly one enabled owned forward accept, scoped by `wg-hub`,
      `src-address=10.99.0.11`, and `dst-address-list=bottega-lab-vlans`,
      placed before the first enabled forward drop.
- [ ] Exactly one enabled owned `change-mss` rule on `wg-hub`.
- [ ] `/ip route print` has the owned static route to `10.99.0.11/32` via
      `wg-hub` (`bottega-phase5-route-roadwarrior`).
- [ ] `/ip service print` shows `www`, `ssh`, `winbox` limited to exactly
      `192.168.88.0/24,10.99.0.0/24`.
- [ ] SSH, WinBox, and MAC-WinBox recovery still work from the LAN.
- [ ] The phase 4 dst-nat and forward rules are unchanged.
- [ ] A second run of the phase 5 playbook, of `bottega-base-lockdown.yml`, and
      of `bottega-phase-4-public-https.yml` each report `changed=0`.

Tunnel, from the phone on **cellular** — never from the LAN:

- [ ] After importing the profile, `/interface wireguard peers print` shows a
      recent handshake and non-zero rx/tx for the road-warrior peer.
- [ ] Proxmox answers at `10.10.0.2:8006` and Traefik at `10.30.0.200:443`.
- [ ] An internal-only `*.ruddenchaux.xyz` hostname resolves to `10.30.0.200`
      and its service answers.
- [ ] WinBox reaches `192.168.88.1` over the tunnel.
- [ ] With the tunnel disconnected, that same internal-only hostname is
      unreachable — proving the tunnel is what granted access.

External, from cellular or the Hetzner VPS:

- [ ] `nmap -Pn -sT -p 22,80,8291,8728,8729 145.11.24.43` — none open.
- [ ] `nmap -Pn -sT -p 443 145.11.24.43` — open, unchanged by this phase.
- [ ] Jellyfin, Home Assistant, and Immich still answer over public HTTPS with
      valid certificates.

A note on scanning UDP `61536`: `nmap -Pn -sU` will report `open|filtered`
whether or not the listener exists, because WireGuard never replies to an
unauthenticated packet. That result is not evidence either way — a successful
handshake from the phone is the only real proof the listener is reachable, and
the absence of one is the only real proof it is not.
